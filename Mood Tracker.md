# GlowPath (Mood Tracker) — backend-first web service

**Статус:** схема БД + auth готовы → CRUD записей / тегов / вложений
**Старт:** июль 2026
**Тип:** личный + учебный проект
**Фокус:** backend + tooling; потом frontend. **Деплой и статистика — после рабочего приложения.**
**Приоритет:** **полный** — Game Review Analyzer на паузе

> Веб-сервис для трекинга настроения. Не коммерческий продукт — рабочее приложение для прокачки backend-навыков с ИИ-агентами: код, тесты, деплой, инфраструктура «как на реальных проектах».

---

## Зачем этот проект

**Учебное (главное):** сделать **рабочее** приложение, задеплоить, настроить ruff / mypy / make / Docker / pytest — всё, что пригодится на работе и собеседованиях. Разработка с ИИ-агентами как часть процесса.

**Личное (вторично):** трекинг настроения для себя. **Не связан** с Obsidian vault и [[Lifestyle/Journal/_index|Journal]] — отдельный продукт.

**Не цель:** обогнать Daylio, монетизация, публичный SaaS, светить в открытый интернет.

## Цель первой фазы (backend MVP)

Рабочий **REST API** + **PostgreSQL** + **MinIO** + **Docker Compose** (локально), через который можно:

1. Зарегистрироваться / войти (email+пароль и Google OAuth).
2. Создавать несколько записей настроения в день: оценка 1–5 (эмоция + эмодзи), дата/время, заметка до 500 символов, теги из групп, вложения (фото/аудио).
3. Редактировать и удалять записи **без ограничения по возрасту**.
4. Управлять своими группами тегов и тегами (CRUD).
5. Фильтровать записи по дате (в часовом поясе пользователя).

**После backend:** frontend; **статистика и деплой** — когда приложение стабильно локально.

**Не в первой фазе:** графики/агрегаты, деплой, ML-инсайты, экспорт, push, мобилка.

## Доменная модель

| Сущность | Поля / правила |
|----------|----------------|
| **User** | email, пароль (хэш), OAuth (Google), **`timezone`** (IANA, напр. `Europe/Minsk`); изоляция данных |
| **MoodEntry** | `user_id`, `recorded_at` (UTC в БД), `score` (1–5), `note` (≤500), связь с тегами и вложениями |
| **TagGroup** | принадлежит пользователю; `slug` + JSONB `labels` `{en, ru}`; `sort_order` |
| **Tag** | в группе пользователя; `slug` + JSONB `labels`; `sort_order` |
| **MoodEntryAttachment** | `kind` (`photo` \| `audio`), метаданные + `storage_key` в MinIO |

PK везде **UUID**. Таблицы: `users`, `mood_entries`, `tag_groups`, `tags`, `mood_entry_tags`, `mood_entry_attachments`, `auth_tokens`.

### Правила записей

| Правило | Решение |
|---------|---------|
| Записей в день | **Несколько** — каждая с отметкой времени (`recorded_at`) |
| Поля записи | **Оценка + дата/время + заметка** (+ теги + вложения) |
| Редактирование | **Без ограничения по времени** — можно править запись любого дня |
| Дубликаты по времени | **Разрешены** — несколько записей в одну секунду ок |
| Заметка | **≤500 символов** (текст); фото/аудио — отдельно |
| Вложения | До **5 фото** + **1 аудио** на запись; файлы в **MinIO** |

### Шкала настроения (1–5 = эмоция + эмодзи)

Число в API и БД — **целое 1–5**. Клиент и OpenAPI отдают расширенное представление (лейбл + эмодзи). Дефолтный маппинг на backend (`core/mood_scale.py`); пользователь может переименовать уровни в **mood preferences** (поле `label` в `score_styles`).

| Score | EN | RU | Emoji |
|-------|----|----|-------|
| 1 | awful | ужасно | 😢 |
| 2 | bad | плохо | 😞 |
| 3 | neutral | нейтрально | 😐 |
| 4 | good | хорошо | 🙂 |
| 5 | great | отлично | 😄 |

*`score` и группа тегов «Настроение» — независимые слои:* у записи может быть `score=4` и тег «Усталость».

*Кастомные названия хранятся как строка-override (не `{en,ru}`); пустая строка в PATCH сбрасывает к дефолту локали. Подписи и эмодзи по умолчанию — в `mood_scale.py`.*

### Фон дня из цветов настроения (frontend)

На ленте записей у каждой секции дня (`.day-section`) лёгкий пастельный фон, собранный из **цветов score** пользователя (preferences / дефолты).

**Визуальная система** живёт в `frontend/src/design/`:

| Система | Модули | Роль |
|---------|--------|------|
| **Chrome** | `chrome.ts` + `--chrome-*` в `index.css` | UI без mood: surfaces, text, borders, actions |
| **Semantic Mood** | `moodTheme.ts`, `gradientEngine.ts`, `gradientRecipes.ts`, `oklab.ts` | Один hex → surfaces / glow / accent / gradients |
| **Motion** | `motion.ts` + `--motion-*` | Общие duration / easing |

**Mood Theme Builder** (`buildMoodTheme(hex)`): пользователь задаёт один цвет; движок отдаёт `surface50…300`, `accent`, `glow.xs…lg`, `subtle`, `text`, `muted`, `cssVars` (audio). Интенсивность (`calm` \| `moderate` \| `expressive`) масштабирует wash/chroma/glow без смены API цвета.

**Gradient Engine** + **recipes**: `day` / `week` / `weekStrip` — одни и те же OKLab-формулы, разные пресеты. Применение дня: `buildGradientWashFromScores` в `EntriesPage`. Compat: `lib/dayMoodWash.ts` реэкспортирует старый API.

**Идея wash:** смешивать в **OKLab**, осветлять, градиент с учётом **порядка записей** — день «радость → грусть» ≠ «грусть → радость».

#### Алгоритм (recipe `day`)

1. Записи дня, `recorded_at` по возрастанию.
2. Score → hex (`getMoodScoreColor`).
3. Hex → OKLab → wash (`washStrength`, `chromaScale` из recipe).
4. Якоря: start `(n−i)^orderPower`, end `(i+1)^orderPower`, mid равные веса если `n ≥ midStopMinColors`.
5. CSS: solid или `linear-gradient(angleDeg, …)`.

#### Параметры recipe `day` (`gradientRecipes.day`)

| Параметр | Default | За что отвечает |
|----------|---------|-----------------|
| `washStrength` | `0.82` | Осветление к белому |
| `chromaScale` | `0.48` | Насыщенность после wash |
| `orderPower` | `1.35` | Сила temporal bias |
| `angleDeg` | `148` | Угол градиента |
| `midStopMinColors` | `3` | Когда добавлять mid stop |

Glow иконок: `moodGlowFilter(hex)` (уровень `sm` = исторический `drop-shadow(…88)`). Подсветка прыжка с календаря (`.day-section-highlight`) не перетирает wash — только chrome focus-ring + `saturate`.

### Часовой пояс

**Решение:** в БД всё хранится в **UTC**; у пользователя в профиле — **IANA timezone** (`Europe/Minsk`, `Europe/Warsaw`…).

**Как это работает (простыми словами):**

1. Пользователь в Бресте выбирает timezone `Europe/Minsk` (или определяем при регистрации / из браузера).
2. Запись «сегодня в 14:30» клиент отправляет как ISO-8601 с offset **или** как локальное время + timezone на сервере конвертируется в UTC.
3. Фильтр «записи за сегодня» сервер считает **границы дня в timezone пользователя**, потом ищет в UTC.
4. В ответах API можно отдавать `recorded_at` в UTC + опционально `recorded_at_local` для UI.

Так «день» у пользователя в Минске не съезжает из-за сервера в другом регионе.

**Дефолт при регистрации:** `Europe/Minsk` (можно сменить в настройках).

### Теги, группы и локализация (i18n)

**Приоритет языков:** `ru`, `en`.

**Модель:** у каждого пользователя свои **группы** и **теги** (`user_id`). Глобальных системных строк в БД нет.

**Подход:** `slug` + **JSONB `labels`**, без отдельной таблицы переводов.

```json
{
  "slug": "work",
  "labels": { "en": "Work", "ru": "Работа" }
}
```

| Аспект | Решение |
|--------|---------|
| Владение | Группы и теги **принадлежат пользователю**; полный CRUD |
| Дефолты | Шаблон в `core/default_tag_groups.py` — **копируется при регистрации** |
| В связях с записями | FK на `tag.id` (UUID) |
| Ответ API | Поле **`label`** — по `Accept-Language` или `?locale=ru` |
| Fallback | `en` → если нет перевода |
| Кастомные теги | Тот же формат `slug` + `labels` (можно заполнить один язык) |

**Дефолтные группы (шаблон):**

| Группа (slug) | Теги |
|---------------|------|
| `weather` — Погода | sunny, cloudy, rain, thunderstorm |
| `sleep_quality` — Качество сна | slept_well, average_sleep, slept_poorly |
| `mood` — Настроение | joy, anxiety, fatigue, calm |
| `activity` — Активность | work, sport, social, rest |

**Не делаем в MVP:** gettext, полный CMS переводов, автоопределение языка заметок.

### Вложения

| Kind | Лимит | Хранение |
|------|-------|----------|
| `photo` | до 5 на запись (`position` 1–5) | MinIO; в БД — `storage_key`, mime, size, original_name |
| `audio` | 1 на запись | то же |

## Пагинация: offset vs cursor

**Решение для MVP:** **offset** — достаточно для маленького проекта и простых списков записей.

**Учебная задача (для собеседований):** разобраться, **когда нужен cursor-based pagination** вместо offset.

| | Offset | Cursor |
|---|--------|--------|
| Как работает | `LIMIT n OFFSET m` — пропустить m строк | Ключ последней записи (`created_at`, `id`) — «дай следующие n после X» |
| Плюсы | Просто, понятные страницы «стр. 2 из 10» | Стабильно при вставках/удалениях; лучше на больших таблицах |
| Минусы | Медленно на больших offset; дубли/пропуски при изменении данных во время листания | Нет произвольного «перейти на страницу 47» |
| Когда уместен | Мало данных, админки, прототипы | Ленты, чаты, infinite scroll, миллионы строк |

→ Вынести в [[IT/Stack/_index|Stack]] отдельной заметкой, когда разберёмся на практике.
